# keenetic/

Маршрутизация сетей Meta (Instagram, Facebook, WhatsApp) через отдельный
шлюз или VPN-интерфейс: список сетей + генератор команд.

| Файл | Назначение |
|---|---|
| `meta-routes.sh` | Генератор команд маршрутизации по списку сетей Meta. Формат `route add ... mask ... <шлюз>` (основной), формат Keenetic CLI `ip route ... auto`, а также применение маршрутов прямо на роутере Keenetic через `ndmc` (нужен Entware). |
| `meta-routes-add.txt` | Готовый список `route add <сеть> mask <маска> 0.0.0.0` — 52 записи. |
| `meta-routes-del.txt` | То же для снятия: `route delete <сеть> mask <маска> 0.0.0.0`. |
| `meta-routes-add-cli.txt` | Тот же список в формате Keenetic CLI (`ip route ... Wireguard0 auto`) для вставки в веб-CLI роутера. |
| `meta-routes-del-cli.txt` | Снятие маршрутов в формате Keenetic CLI (`no ip route ...`). |

## Формат `route add`

```
route add 157.240.0.0 mask 255.255.0.0 0.0.0.0
```

Шлюз задаётся параметром, по умолчанию `0.0.0.0`:

```sh
sh meta-routes.sh route                # шлюз 0.0.0.0
sh meta-routes.sh route 192.168.1.2    # свой шлюз
sh meta-routes.sh route-del 192.168.1.2
```

В Windows постоянные маршруты (переживают перезагрузку) добавляются
ключом `-p`: `route -p add ...`; при шлюзе `0.0.0.0` может понадобиться
указать интерфейс — `route add ... 0.0.0.0 if <номер>` (номера интерфейсов
показывает `route print`).

## Формат Keenetic CLI

```sh
sh meta-routes.sh cli Wireguard0       # ip route ... auto
sh meta-routes.sh cli-del Wireguard0   # no ip route ...
```

Порядок настройки на роутере:

1. Поднимите VPN-подключение и **снимите** галку «Использовать для выхода
   в Интернет» — иначе весь трафик уйдёт в туннель.
2. Узнайте системное имя интерфейса: *Управление* → *Диагностика* →
   *Командная строка*, команда `show interface` (обычно `Wireguard0`,
   `OpenVPN0`, `L2TP0`, `Proxy0`).
3. Вставьте содержимое `meta-routes-add-cli.txt` в командную строку;
   если имя интерфейса другое — сгенерируйте файл заново
   (`sh meta-routes.sh cli OpenVPN0`).
4. Проверка: `show ip route`. Откат — `meta-routes-del-cli.txt`.

Ключ `auto` означает, что маршрут переустанавливается при поднятии
интерфейса, после перезагрузки роутера повторять ничего не нужно
(последняя строка `system configuration save` сохраняет конфигурацию).

## Запуск на самом роутере (Entware)

```sh
mkdir -p /opt/scripts
# скопировать meta-routes.sh в /opt/scripts (scp, wget, vi)
sh /opt/scripts/meta-routes.sh add Wireguard0     # добавить через ndmc
sh /opt/scripts/meta-routes.sh show Wireguard0    # проверить
sh /opt/scripts/meta-routes.sh del Wireguard0     # откатить
```

## Состав списка

52 записи — исходный список без изменений: 14 отдельных узлов (маска
`255.255.255.255`) и 38 подсетей, в исходном порядке. Подсети намеренно
не объединялись: перекрытия (например, `157.240.251.0/24` внутри
`157.240.0.0/16`) допустимы, более специфичный маршрут просто выигрывает
у более общего. Полный список с комментариями — `sh meta-routes.sh list`.

Записи помечены двумя областями:

- **core** (43 записи) — узлы и диапазоны, анонсируемые Meta
  (AS32934/AS63293);
- **extra** (9 записей) — то, что Meta не принадлежит либо шире её
  реальных выделений: `142.250.0.0/15` и `173.194.10.0/24` — Google,
  `99.84.0.0/16` — AWS CloudFront, `147.75.0.0/16` — Equinix Metal,
  `213.102.128.0/24` — Telia, плюс требующие проверки `45.130.4.0/24`,
  `77.240.43.0/24`, `87.245.208.0/24` и узел `87.245.223.97`.
  Для Google-сетей заворачивание в туннель вредно — уедут и другие
  сервисы.

Только сети Meta, без спорных записей:

```sh
META_SCOPE=core sh meta-routes.sh route
META_SCOPE=core sh meta-routes.sh cli Wireguard0
```

Готовые `.txt` собраны по полному списку (`META_SCOPE=all`).

## Ограничения

- Маршруты статические: если Meta начнёт отдавать адреса из новых сетей,
  список придётся дополнить (секция `nets()` в скрипте).
- DNS не заворачивается: при DNS-блокировках дополнительно настройте
  DNS-over-TLS/HTTPS (на Keenetic — *Интернет-фильтры* → *DNS-серверы*).
